# 消息发送路由与运行控制

## 当前状态

直连 Platform/Desktop 的普通主聊天文本由 `useComposerSend` 派发 `agent:send-message`，`useMessageActions` 经统一数据层发送 `/api/send`，不再按空闲/运行中自行选择 query 或 steer。接口返回收据，Run 事件仍由主 WS 推送和既有 attach 消费。BTW、解读、空消息续跑和带专用 params 的请求沿用旧 Query；“立即继续”仍使用空白 steer。

## 统一发送

- 发送前沿用目标所有权、Agent 可用性、引用与运行选项检查。活动 Run、提问、审批、表单本身不禁用普通文本发送；服务端决定 started、inserted 或 queued，作答仍走 submit。
- `requestId` 兼作幂等键，收据包含 mailId/chatId/delivery/runId。`model` 字段与 `/api/query` 相同（`key`），detail 沿用帧顶层或 HTTP URL 参数。运行选项在新 Run 才生效，插入时不同选项通过 ignoredOptions 提示。
- `features/mailbox/lib/userOutbox.ts` 按登录身份隔离本地待发记录，正文与原始选项保留。消费事件按 requestId 移除待发并投影正式用户消息；消费先于收据到达时不重建气泡。主聊天不显示正常发送／排队的邮件卡片，仅在未送达或结果未知时显示异常提示。
- `recoverUserOutbox` 分页读取当前 Chat 的 pending，按需获取全文；刷新恢复排队消息，启动清库后详情 404 显示“未送达”。可用新 requestId 重发或删除本地记录，没有服务端撤回、清空或取消。
- 收件箱顶部仅显示“收件箱／垃圾箱”；收件箱合并协议 pending/received，两箱分别读取最新记录后统一按 createdAt、mailId 倒序分页，垃圾箱读取 trash 且只读，box 和 status 取交集；角标仍为 pending 的 total。卡片突出类型、时间、右侧状态和发件／收件方，正文仅展示两行预览，点击打开全文；Mail ID 悬停类型标签查看，筛选默认收起。
- mention、owner 优先级和 Agent/newChat nonce 的 canonical 路由提升沿用既有规则，以发送收据中的稳定 chatId 提升；迟到收据不能覆盖已切换的页面。

网关模式仍走原 Query/steer，因为当前 agent-gateway 未转发 `/api/send`；没有为本阶段修改网关部署或协议。

## 保留的 Query 与 steer 路径

专用 Query 继续通过 RunTransport 创建 live session 并维护 abort controller、runId 和事件缓存。旧 PendingSteer 条目保留原控制响应与消费确认、取消和失败恢复规则；新普通文本不创建这种本地等待项。只带引用的输入（直连时走 `/api/send`）与空续跑维持各自的历史及 canContinue 准入。收据 `status` 为 failed/discarded/withdrawn 时直接标未送达，不挂接收据中的 runId。旧队列在 Run 结束后续发有正文消息时进入统一发送入口。

Main Chat 的“新对话重问”是一次有序路由事务，不是两个可独立派发的 UI event。Agent route 先生成一次性 13 位 `newChat` nonce；Desktop 环境等待宿主确认外层 route、guest URL 与无 owner Surface 已统一到该 nonce，Standalone 环境等待本地 route 提交。只有准备完成后才清空旧会话并发送一次无 `chatId` query。准备失败或超时保留来源 Chat 且不发送；稳定 `chatId` 到达后继续使用 replace 收敛同一临时路由。

以下描述仅适用于保留的旧 steer 条目。steer 按 Chat 保存为 `queued`，点击引导后进入 `sending`。控制响应 `accepted:true` 只代表提交被接受，条目继续显示“等待确认”；匹配 `steerId` 的有效 `request.steer` 才确认移除，事件携带的 `chatId` / `runId` 也必须匹配。后台 query / attach 仍处理确认，历史加载也用回放事件校准漏掉的确认；同一 steer 的重复事件不重复创建时间线节点。

明确 `accepted:false` 时，将内容恢复到来源 Chat 的草稿，已有文字保留并在末尾追加。网络错误或缺少 `accepted` 的响应保留 `sending`，标记结果未确认，不自动重发；流已经确认后的迟到响应不再恢复草稿。运行结束只把尚未提交的首条 `queued` 转为普通消息；切换 Chat、切换 Run 或加载历史不触发这一自动发送。`sending` 在运行结束后仍保留，用户可以手动取消并恢复到草稿。

## 边界与非目标
- `RunOwner` 只在前端内部流转，API 不发送 `owner` 属性；序列化后 所有 Agent（包括 TEAM）都只带 `agentKey`。
- 已保存 Team chat 不会因成员 task event 的 `agentKey` 降级为 Agent chat。
- 不在发送流程中解释 tool、content、plan 等事件，这些由 events processor 负责。
- steer、interrupt、compact、remember、learn 等命令的协议字段以后端接口为准。

### 附件 steer

带正文的图片与文件先上传，再通过 `/api/send` 的 references 发送。以下网关模式保留的路径中，运行中粘贴图片继续调用 `/api/upload`，必须等待整组附件就绪；上传失败时保留附件并阻止发送。入队时冻结 `references` 并清空输入区，待发送条展示资源缩略图。提交 `/api/steer` 时携带引用；取消或明确拒绝恢复文字与附件到原 Chat，恢复的附件按 Chat 隔离并可单独删除。响应未知时保留发送状态，等待 `request.steer` 确认；Run 结束时，已有主 query 历史的 queued 项按顺序转 query 并携带引用和展示数据，允许纯附件或纯选区；缺少历史确认的纯引用项恢复输入区并提示补充正文。

实时与历史 steer 时间线均读取事件 `references` 展示附件，空文字附件事件也完成队列确认。同一主 Chat 的首次 query 必须有非空 `message`，后续 query 可只带有效文件、对话或选区引用。空正文且无引用的 query 仅在已有主 query 历史、服务端 Chat 明确 `canContinue:true`，且无活动 Run 或待处理 awaiting 时允许；未知状态不授予空内容续跑能力。普通 Composer steer 要求文字、有效文件引用或含非空顶层 `text` 的选区引用至少一项。普通文件不要求视觉模型；图片在视觉模型中直接输入，非视觉模型接收文件引用，交由已配置的图片识别工具按需读取，不应因缺少原生视觉能力禁用发送。未支持的远端附件路径以服务端拒绝结果为准。Native wait 卡片的“立即继续”是独立控制入口，直接发送空白 steer，不经过 Composer 的正文/引用校验。Native 活动 Run 可随 steer 添加技能、知识库和对话引用；远端后端拒绝这些定位引用的 steer。后端需先更新到支持附件 steer 的版本，防止旧后端忽略新增字段。

划词引用弹层支持为每条原文编辑可选批注；清空后省略 `annotation`。主聊天、旁聊及独立旁聊共用编辑组件，发送后的时间线与待发送 steer 队列只读展示原文和批注。发送失败保留草稿。仅使用顶层 `text`，不读取 `meta.text`；服务端引用无需 name/sourceKind 即可回放。ID 保持原始值，由 Platform 在模型提示词中映射短编号。首次 query 仍需输入正文，后续 query 与 steer 可只提交有效划词引用。

划词编号使用独立正整数 `annotationIndex`，与 Reference ID 分离，进入请求及历史记录。页面蓝色序号气泡和模型称呼 `Annotation N` 均采用该值，不按文件/图片引用排序；编辑或清空批注不改变编号。编号在划词加入目标对话草稿时分配，主聊天按 chatId、旁聊按 session 隔离，每轮 Run 从 1 开始；Run 完成、取消或失败后重置计数，未发送批注保留原文和批注并从 1 重新编号，历史消息编号不变。同一轮内切回草稿保留编号，删除不复用编号，新建空白对话重置。捕获选区、历史读取与跨窗口解析不推进计数。DOM Range 仅在内存保留；添加引用后在原文附近打开无语音入口的可选批注栏，Enter 收起、Shift+Enter 换行，点击序号再次编辑。原文 DOM 消失或改变时隐藏锚点，引用仍可在片段汇总弹层编辑。

首次判断复用服务端 Chat 摘要 `lastRunId` 和主对话 `request.query` 事件，不以预分配的 `chatId`、本地乐观消息或 BTW/解读事件作为依据；首次请求被拒绝仍需正文，已受理后执行失败或中断可续聊。前端发送按钮、直接发送和排队转 query 共用规则，Platform 最终验证主对话历史及引用。需同步部署支持纯引用后续 query 的 Platform，旧服务端仍会拒绝空正文。

纯批注发送的防重判断包含引用内容，Run 状态、Chat、Run ID 或引用内容变化会释放上一轮发送锁，避免正文持续为空时拦截后续发送。

## 准入失败与输入恢复

普通 Composer 在清空前记录正文、引用（包括附件）、手动技能选择，并将快照绑定实际 query requestId。未被接受的 query 失败时，只有稳定的输入版本未变化才原位恢复；新输入、附件/技能编辑、New Chat 重置及会话切换推进版本。否则保存为未发送内容，提供恢复和丢弃，恢复时追加到已有输入，不覆盖新草稿；已有 Chat 的快照须回到原 Chat 恢复。query 一旦被接受即释放快照，后续执行错误不恢复、不自动重发。失败快照仅存于当前应用运行期。

agent_not_found / agent_configuration_invalid 直接使对应 Agent unavailable 并废弃旧详情检查及缓存；403 映射 forbidden，401 交给认证恢复。interaction_disabled 刷新当前 Agent 能力；skill_reference_unavailable 刷新技能目录并保留拒绝提示。历史 owner 不随这些状态变化改写。
