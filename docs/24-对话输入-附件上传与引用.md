# 附件上传与引用

## 当前状态
Composer 上下文由 `useComposerAttachments`、`composerAttachments.ts`、`ComposerAddMenu` 和 `ComposerAttachments` 负责。上传接口仍为 `/api/upload`；本地文件、Chat 与 Site 统一通过既有 `references` 随消息发送。

## 核心职责
- “+”入口打开向上弹出的 Add、Mode、Skills 分组菜单；只有“本地文件”会触发隐藏 file input。
- 支持文件选择、拖拽、粘贴和 Desktop 截图转附件，网盘文件本期为禁用占位。
- Chat 弹窗刷新 `/api/chats`、排除当前对话，并以 `type + id` 去重。
- Site 弹窗通过 Desktop `desktop:webs:list` bridge 读取 Websites 与 Webapps；浏览器环境显示不可用。
- 为图片创建本地 preview URL，并在清理时 revoke。
- 上传文件后保存 resource URL、references 和附件展示元数据。
- Chat/Site 使用独立 `ReferenceCard`，不进入文件下载或资源预览逻辑。
- 在发送前阻止仍在 uploading 或 error 状态的附件。

## 核心流程
用户添加文件后生成 pending attachment，随后调用 `uploadComposerAttachments`。后端返回 chatId、references 和 resource URL 后，附件进入 ready 状态。Chat/Site 在二级弹窗确认后直接生成 ready 上下文卡片。发送消息时，所有 ready 项的 references 进入 query payload，attachments 元数据用于用户消息和回放展示。

New Chat 的已上传引用与上传所属 Chat 身份属于同一份运行期草稿。切换历史 Chat 或重新挂载 Composer 后，两者必须一起恢复；历史 Chat 的上传与清理不能覆盖共享 New Chat 的上传身份。发送时使用该身份提交 query，消费草稿时清理，受理前失败恢复时一并还原。此状态不持久化到浏览器存储，也不改变 Desktop 或 Platform 的身份授权边界。

Desktop WorkPanel 图片评审交接和 macOS 原生共享导入先创建 `staged` 本地附件，不在交接时调用 `/api/upload`。图片评审仍只接收有界 PNG；原生共享保留源文件类型与正文，包括微信聊天记录 ZIP，不解包、不把文件内容视为用户指令。同名原生共享附件以新的显示文件名追加，保留已有附件、文字与技能草稿。用户点击发送后，Composer 才把 staged 附件切为 uploading，沿相同 `uploadComposerAttachments` 链路取得 references；上传全部成功后继续本次用户已确认的发送，失败则保留草稿和可重试附件且不发送 query。移除附件、切换/清理 Composer 或卸载时必须同步释放 staged File 和 preview URL。

原生共享在上传成功前保留宿主批次与一次性分享路由，刷新该新对话仍可重新读取本机原文件。用户确认发送且全部附件持久上传成功后，WebClient 才向 Desktop 确认接收并移除分享参数；确认失败继续保留路由、草稿和已上传引用，阻止 query，并提供同页重试。普通浏览器与 WorkPanel 子 Surface 不获得原生共享文件读取能力。

原生共享的公共接口与协议必须品牌无关，WebClient 不按 CuteJ、ZenMind 或聊天应用选择 bridge。微信是首个来源，架构必须承接后续飞书、企业微信、QQ 等导入；来源获取和专用聊天格式解析在各自适配中扩展，仍交付同一附件草稿与用户发送流程，不增加独立 Composer 或自动提交入口。原始文件可通过通用链路传入，不等同于对应应用的真实入口和格式已完成支持。

Chat 引用结构为 `{ type: "chat", id, name, meta }`，Site 引用结构为 `{ type: "site", id: entryKey, name, url?, meta: { kind, updatedAt? } }`。前端字段只用于选取和展示，后端仍会按可信 ID 重新校验或展开。

## 上传接口与 file 引用

`POST /api/upload` 使用 multipart/form-data。字段如下：

| 字段 | 说明 |
|---|---|
| `file` | 上传文件，uploadFile 使用 File.name 或 filename 作为文件名 |
| `requestId` | 可选，uploadFile 未提供时自动生成 |
| `chatId` | 可选；首次省略会创建占位 Chat，后续文件带返回的同一 chatId |
| `agentKey` | Platform 支持的可选 Agent 绑定字段；当前 uploadFile helper 不发送 |
| `name` | Platform 支持的可选 Chat 名称，不是上传文件名；当前 helper 不发送 |
| `sha256` | uploadFile 仅在调用方提供时发送；Platform 不读取，自己计算文件摘要 |

响应为 `{code:0,msg:"success",data:{requestId,chatId,upload}}`。无 chatId 时创建的占位 Chat 在首条正式请求前不进入历史列表，可用于 query 或 execute。

`extractUploadReferences(response.data)` 将 upload 转为一条 file 引用，`extractUploadChatId(response.data)` 取得上传所属 Chat：

```json
{
  "id": "r01",
  "type": "file",
  "name": "receipt.png",
  "path": "/chat/receipt.png",
  "mimeType": "image/png",
  "sizeBytes": 1234,
  "url": "@chat/receipt.png",
  "sha256": "<平台计算的摘要>"
}
```

path 可能是运行环境映射路径，应保留上传返回值，不自行拼宿主路径；稳定资源引用使用不含 chatId 的 `@chat/<name>`，需与所属 chatId 一起使用。Chat 与 Site 引用结构见上文。

| 消费入口 | 规则 |
|---|---|
| `/api/query` | references 与 Chat 身份一起提交，遵守 Agent interactionConfig 与现有引用准入 |
| `/api/steer` | 支持当前 Chat 的已上传文件；不支持 Chat/Site 等引用 |
| `/api/execute` | 可选 chatId、references，沿用 Query 准入；chatId 与 multipart 文件互斥，message 必填，见执行测试专题 |

图片作为视觉输入要求视觉模型（IsVision）、受支持的图片 MIME，且文件可读取并满足大小限制；非视觉模型只看到文件名等引用文本。当前图片加载失败会跳过图片，不能凭结构化交卷成功认定模型已经看图。

Composer 与执行测试页共用 uploadFile 和两个 extract helper。Composer 维护附件草稿；执行测试页直接以 references JSON 文本框为唯一引用数据源，上传只是向 JSON 追加。

## 边界与非目标
- 附件上传不等同于 artifact 发布；artifact 是运行中后端事件 `artifact.publish`。
- steering 活跃 run 时支持当前 Chat 已上传图片和普通文件引用（包括 HTML、MD），允许纯附件和混合附件；Chat、Site 引用仍不支持。文字和有效附件不能同时为空，上传失败或未完成时不能发送。同一主 Chat 的首次 query 要求非空正文，后续 query 可只带有效文件、对话或选区引用，仅最后一次主 Run 明确异常结束或取消后允许正文和引用均为空以表示继续；空 steer 仍拒绝。
- 前端不读取文件内容做协议解释，只负责上传、预览和发送引用。
