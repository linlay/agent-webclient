# 附件上传与引用

## 当前状态
Composer 上下文由 `useComposerAttachments`、`composerAttachments.ts`、`ComposerAddMenu` 和 `ComposerAttachments` 负责。上传接口仍为 `/api/upload`；本地文件、Chat 与 Site 统一通过既有 `references` 随消息发送。

## 核心职责
- “+”入口打开向上弹出的 Add、Mode、Skills 分组菜单；只有“本地文件”会触发隐藏 file input。
- 支持文件选择、拖拽、粘贴和 Desktop 截图转附件，网盘文件本期为禁用占位。
- Chat 弹窗刷新 `/api/chats`、排除当前对话，并以 `type + id` 去重。
- Site 弹窗通过 Desktop `desktop:webs:list` bridge 读取 Websites 与 Webapps；浏览器环境显示不可用。
- 为图片创建本地 preview URL，并在清理时 revoke。
- 上传文件后保存 resource URL、references 和附件展示元数据。
- Chat/Site 使用独立 `ReferenceCard`，不进入文件下载或资源预览逻辑。
- 在发送前阻止仍在 uploading 或 error 状态的附件。

## 核心流程
用户添加文件后生成 pending attachment，随后调用 `uploadComposerAttachments`。后端返回 chatId、references 和 resource URL 后，附件进入 ready 状态。Chat/Site 在二级弹窗确认后直接生成 ready 上下文卡片。发送消息时，所有 ready 项的 references 进入 query payload，attachments 元数据用于用户消息和回放展示。

Chat 引用结构为 `{ type: "chat", id, name, meta }`，Site 引用结构为 `{ type: "site", id: entryKey, name, url?, meta: { kind, updatedAt? } }`。前端字段只用于选取和展示，后端仍会按可信 ID 重新校验或展开。

## 边界与非目标
- 附件上传不等同于 artifact 发布；artifact 是运行中后端事件 `artifact.publish`。
- steering 活跃 run 时不支持携带任何文件、Chat 或 Site 引用。
- 前端不读取文件内容做协议解释，只负责上传、预览和发送引用。
