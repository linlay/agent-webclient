# 消息发送路由与运行控制

## 当前状态
消息发送由 `useComposerSend` 和 `useMessageActions` 协作完成。前者负责本地输入决策、slash 命令、steer 队列和 send event，后者监听 `agent:send-message` 并创建 query stream session。

## 核心职责
- 解析目标 chat、`RunOwner`、附件 references、运行参数和模型覆盖。
- 阻止同一会话重复并发发送，支持不同会话切换时 detach 当前 run。
- 在 streaming 状态下将普通输入转为 steer，且禁止带附件 steer。
- 管理 abort controller、requestId、runId、live session 和 timeline user message。

## 核心流程
用户触发发送后，`useComposerSend` 先处理 slash command 和 steer 场景，再派发 `agent:send-message`。`useMessageActions` 接收事件，解析 mention 和 preferred routing，创建 requestId，启动 SSE/WS executor，并将收到的事件交给 timeline handler。owner 优先级固定为已保存 chat、当前 run/session、再到新会话选择的 Agent 或 Team。Team 使用 `{ kind: "orchestrated-team", teamId }`，query 只发送 `teamId`；Team 内 `@成员` 保留在消息文本中交给协调器，不会改写 owner。只有原 query 不带 `chatId` 且归一化事件提供稳定 `chatId` 时，才通知 agent 路由把 `?newChat=` replace 为 `?chatId=`；失败、取消或没有稳定 ID 时不改变地址。

## 边界与非目标
- `RunOwner` 只在前端内部流转，API 不发送 `owner` 属性；序列化后 Agent 只带 `agentKey`，Team 只带 `teamId`。
- 已保存 Team chat 不会因成员 task event 的 `agentKey` 降级为 Agent chat。
- 不在发送流程中解释 tool、content、plan 等事件，这些由 events processor 负责。
- steer、interrupt、compact、remember、learn 等命令的协议字段以后端接口为准。
