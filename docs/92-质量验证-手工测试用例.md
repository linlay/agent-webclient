# 手工测试用例

## 当前状态
本项目以 Jest 单元测试为主，核心联调依赖外部 AGENT API、语音服务、Desktop 宿主和浏览器能力。手工测试用于覆盖代理、实时流、HITL、附件、Viewport、语音和发布包结构等跨系统场景。

## 核心职责
- 给出本地开发和 Program Bundle 的最小检查路径。
- 覆盖 SSE/WS、attach、submit、steer、interrupt 等运行控制。
- 覆盖附件上传、artifact resource、viewport iframe、HITL 四种 mode。
- 明确哪些失败应回到后端协议或部署配置排查。

## 核心流程
先准备 `.env`，显式设置 `DESKTOP_APP=false` 并启动 `make dev`。确认页面可打开、agents/chats 按当前 backend 能力表通过主 WebSocket 加载，再执行一次普通 query、一次运行中 steer、一次 interrupt、一次带附件 query。随后用后端可触发的样例验证 artifact.publish、viewport block、frontend tool、question、approval、form、plan awaiting 和 voice。

## Tool 过程终端回归

1. 让 Native Host Bash 在 `/Users/linlay/Project/cligrep/cli-mock` 执行 `./mock qr-login --wait 5s`，确认第一条 `tool.output` 到达后工具卡只自动展开一次，运行区不显示 command、cwd、description 和 timeout 参数，也没有独立边框或底色；二维码所有行立即显示，前导空格和方块字符对齐，终端没有 8 行裁剪，位于列表底部时也没有悬浮运行指示遮挡内容。

   - 在 Desktop Main Chat 的时间线空白处按普通 `←/→`，确认 WebClient 分别发出 left/right 工作区消息，Desktop 切换左侧栏/当前 Chat WorkPanel 且焦点仍在 guest。输入框、contenteditable、按钮、链接、菜单、tabIndex 选项、Monaco/终端、文字选区、修饰键、repeat、IME composition、pointer/drag 期间不得发送。准备 active awaiting/HITL 后在选项及页面空白处回归 `←/→`、`↑/↓` 和数字选择，确认全部保留给现有 WebClient 键盘逻辑；awaiting 结束后空白区左右键恢复。Standalone、管理页和 WorkPanel guest 不安装该快捷键。

   - 在 Standalone 单独验证 `/history` 默认 All，`/history?agentKey=<有效 Agent>` 初始化对应筛选且可切换，未知 Agent 在 Agents 与 Chats 都加载完成后回退 All；选择记录通过 Router 导航到 `/agent/:agentKey?chatId=...`。源码与构建产物中不存在 Desktop history-open-chat 请求模块。
5. 根页面 Debug Panel 的 `chat.start` 行应提供 Agent、Copilot、Overview、Debug、Terminal 入口；事件或对应 chat 含合法 `shareId` 时再提供 `/share/{shareId}` 入口。不得用普通 `chatId` 拼接公开分享 URL。
6. Standalone Terminal 覆盖 open/status/write/resize；关闭 Surface 或切换 route 只 detach，关闭 tab 才 close。Desktop `/terminal` 显示 Frame Port unsupported，网络面板不得出现 guest `/ws`。
7. 连续切换 50 次路由，listener 回到基线；长流观察 pending/observer/timer 不持续增长；StrictMode 不产生重复 inbound/push 注册。历史 Chat 快速切换期间，即使 Timeline 数据、容器宽度或书签变化导致滚动恢复 Effect cleanup，同一事务也必须使用剩余期限继续恢复，且 `/api/chat` 成功并进入 `restoring` 后最多 2000ms 进入 `ready`、撤销 busy 骨架；超时路径允许当前位置存在轻微偏差，但不得显示错误层、重复请求 `/api/chat` 或由旧事务覆盖新目标。
8. 设置 `DESKTOP_APP=true`：Frame Port 缺失时看到 `DESKTOP_BRIDGE_UNAVAILABLE`，transport version 错误时看到 `DESKTOP_BRIDGE_INCOMPATIBLE`。新聊天 query 不含预造 runId，只有关联 stream identity 后 URL 才获得稳定 chatId；`chat.created` 只更新列表。guest `/ws` 为 0，Main 保持单物理 Platform WS。
9. Desktop 执行 `sleep 120`：100～105 秒不出现 `WS_DISCONNECTED`、第二次 logical open 或新逻辑 Session；120 秒后 `run.finished` 直接进入原 Chat，无需切换页面。重复多次并持续 30 分钟，不能出现重复 Run、丢终态或待处理 Promise 泄漏。
10. Desktop 在已收到 Run acceptance 后强制断开物理 WS：状态进入 reconnecting，原 stream 不报错；恢复后只从 `lastSeq` 连续显示，不能重新 query。重连期间新的一次性请求返回 `PLATFORM_CONNECTION_UNAVAILABLE`；永久 Frame Port close 时待处理操作统一返回 `DESKTOP_FRAME_PORT_CLOSED`。
11. Standalone 检查真实 `/ws` 首帧必须是 connected v2，协商存活参数合法；持续业务帧可以维持连接，真实静默超过阈值才出现 `WS_DISCONNECTED`。错误版本、字段缺失和越界存活参数返回 `PLATFORM_WS_PROTOCOL_MISMATCH`，不继续运行。

12. 在 Standalone 和 Desktop WorkPanel Overview 中分别点击文件修改行：首次点击在当前 Overview 内展开 original/current 差异并显示加载或错误状态，再次点击收起，加载成功后重复展开复用缓存；两种环境均不得新建 File Diff tab。

13. 从 Main Chat 打开 Overview、Debug、BTW、Source、Planning、Artifact、Reference、File、File Diff 与 Skill，确认使用各自判别式 context 和 canonical WorkPanel descriptor；Skill context 只包含非空 `key`，重复打开只激活已有标签；Artifact/Reference 的 `module` 与 context 保持各自契约，但 route 都落到 Resource。Desktop 缺少 `currentWorker.workspaceDir` 时点击 POSIX、Windows 盘符或 UNC File 路径仍立即创建 File WorkPanel；分别使用包含和不包含 `Project/project` 的路径，File 都必须通过 management Frame Port 发送 `/api/file`，真正的 Project 页仍保持 Project 身份。文件内容正常显示；请求 `/etc/hosts` 时面板保持打开并原样展示 Platform 403，Frame Port 断开时不回退 HTTP、不显示 guest 第二条物理 `/ws`。Realtime Inspector 中 File 只有普通 request/response，不产生 query、attach 或 detach。除 Project 指定 Run/Diff 外 descriptor/URL 不含 `runId`。Web item 继续直接承载目标 HTTP(S) URL，Standalone Web 则使用全局 `/web-viewer` 且不含 Agent/Chat/Run。Overview/Debug 在 Desktop 中仅发送由宿主本地拦截的虚拟 attach，隐藏后重新激活时刷新 `/api/chat`；跨 Chat projection 隔离正确。构造本地 replay 淘汰后再以旧游标打开 Overview，确认首次 `seq_expired` 自动重新加载快照并使用新游标订阅；若新快照仍过期，只显示一次稳定错误和“重试”按钮，不循环刷新、不新增上游 attach，手动重试后才开始新的恢复周期。

14. Platform 连续发送 N 条 delta，原生 WebSocket 和 Desktop socket factory 都投影 N 个同序 event。切换 Main/Copilot/Kanban 时只 detach 一次，detach frame 先于新 query/attach；返回后从 lastSeq attach。四类本地拒绝和 Platform 4xx 均生成等价 `ApiError`。

15. 注入一个 Router 内组件渲染异常和一个 Router 外应用装配异常，均应显示 WebClient 错误页、错误摘要、技术详情与恢复按钮；不得出现空白页、无限 loading 或只有控制台错误。

Desktop 宿主回归时，确认 guest storage、URL 和 DevTools 都不出现 access token。服务冷启动直接进入 `/agent/:agentKey` 时，首个数据请求允许为 WS `/api/agent`，不依赖 `/api/agents` 预热，页面不得出现 `Failed to load agent`，且 Inspector 中只有一个有效 logical socket；`/api/agents`、`/api/agent` 与后续 `/api/chat` 均通过 Main Broker 的 Platform Socket request/response frame 完成。人为延迟 surface 登记时应在 Desktop 规定窗口内恢复；永久缺失时不得转发到 Platform。注入握手前 `1008 + surface_unavailable` 等带 reason 的 close，错误/debug 信息应包含 reason 而不是缺少 access token；显式 Retry 可重新请求，且不得自动重试或回退 HTTP。真正要求 token 的 Standalone Platform 模式在 token 为空时仍显示缺少凭据。WS 401 页面显示重新登录提示，网络异常显示网络提示且不得回退 HTTP。`/ws` 的 HTTP/Upgrade 以及 query、attach、submit、interrupt、steer、access-level HTTP 请求均应被 host 固定拒绝且不触达 Platform。Main Chat route bridge 日志必须按 `router-ready → bridge-received → router-navigate → router-applied` 收敛；Router listener 注册前 Desktop 不发送命令，暖态切换立即发送，地址栏相等但 `useLocation()` 不等时仍以 `replace + flushSync` 提交。快速 A→B→C 只允许 C 的精确 location 确认 C，B 的迟到 render 不得产生 APPLIED 或重复 `/api/chat`。分别通过 Desktop Cmd+K、新建按钮进入 New Chat，并在 `?newChat=` 页面切换到另一个 Agent；即使物理地址栏先变化，React Router、worker 与空白 Timeline 也必须同步到目标，旧 Chat/Agent 内容不得保留。用 Desktop 的 New Chat 发送首条消息后，应从 `?newChat=` replace 为稳定 `?chatId=`，并由 Desktop 外层路由选中该对话；query 失败、取消或没有稳定 ID 时不得改变当前选中项。

已读链路回归：准备不在 `state.chats` 缓存中的 unread Chat，分别由 Desktop Cmd+K 与 Sidebar 直接路由打开。确认 `/api/chat` 详情含完整 summary，切换处于 loading/applying/restoring 时没有 `/api/read`；Timeline 提交并 ready 后 WebClient 经 Frame Port 恰好发送一次 `{chatId, runId}`。已读 Chat、加载失败和 A→B→C 中迟到的 B 都不得发送。让当前可见 Chat 完成更新 Run 并收到 `chat.unread`，确认只为新 `lastRunId` 再发送一次。并发注入旧详情响应与更新 `chat.read` Push，最终 read 状态必须由 `readAt/readRunId` 较新者胜出，且 read 不改变 Chat `updatedAt` 排序。

发布验收必须先校验 Frame Port contract hash，再渲染 Program manifest 并确认无 `/auth`、`/ws`、SSE 特例，且 `/api` 为带 `agent-platform-access-token` 的 HTTP-only route。Frame Port Desktop、匹配 WebClient 和旧任一侧混用都必须明确阻断；Standalone `localhost:11948` 仍保留自己的 `/ws`。

Desktop 右键回归覆盖用户/助手消息、代码、Web 链接、Workspace 文件、Markdown 资源与 AttachmentCard：无选区复制所属原文，有选区只复制选区；链接复用右侧 Web Preview，文件复用 Workspace Preview，资源复用鉴权预览/下载。流式更新、虚拟列表卸载和坐标漂移后执行旧命令必须无操作。抓取 resolve 响应确认不含正文、代码、路径、Token、Bearer、资源临时 URL 或菜单文案。普通浏览器右键事件不得被取消。

## Chat 阅读位置恢复回归

1. 分别在 Main、独立 Agent 和 Copilot 打开同一个长 Chat，滚动到三个不同位置，再切到另一 Chat 后返回；三个 Surface 应恢复各自位置，互不共享书签。不同稳定 `chatId` 的切换在 Router 提交首帧只能看到覆盖时间线的骨架层，不得看到旧 Chat 或目标 Chat 的滚动过程；从点击到骨架出现不超过 100ms。`/api/chat` 返回有效 `activeRun.runId` 时应立即撤掉骨架并显示 replay Timeline，后台 attach 不得重新打开骨架；没有 activeRun 的历史 Chat 必须等 Timeline 渲染和阅读位置恢复完成。快速历史响应时骨架完整展示约 160ms，再用约 80ms 渐隐；减少动态效果时满足位置恢复和 160ms 后直接移除；慢恢复在位置稳定后再完整执行约 80ms 渐隐。同 Chat 后台恢复、New Chat 首次创建和 new Chat live promotion 不触发历史骨架。
2. 在长 Chat 中停留中部，记住一条可辨认消息及其顶部偏移，切换后返回；应优先恢复原锚点。删除锚点后重复验证，依次接受后邻、前邻和合法原索引回退。删除全部候选、清除 bookmark 或改变数据/布局签名后，应直接恢复到对话最后，不得跳到随机位置。
3. 在 Chat 底部切出再返回，应使用瞬时定位恢复最新底部；在中部切出再返回也只能瞬时定位。DevTools 或测试桩中确认所有恢复调用均为 `behavior: "auto"`，并确认中部 offset 或底部状态连续两个动画帧稳定后立即进入 `ready`。恢复 Effect cleanup 后同一 `seq + targetChatId` 必须重新启动，且 2000ms 总期限不得重置；期限内仍不稳定时保留当前最佳位置并进入 `ready`，不得转为错误或触发 `/api/chat` 重试。
4. 恢复后手动向上滚动，再让当前 Run 输出或执行 active run attach；页面不得抢回底部。停留底部时新增输出可以平滑跟随。运行状态从 idle 变为 running 本身不得触发滚动。
5. 用户主动发送消息后应平滑到底部；手动上滚后点击“回到底部”按钮也应平滑到底部。后台 replay、Chat 加载和 attach 不得生成相同滚动请求。
6. 将 `/api/chat` 延迟后快速执行 A→B→C，并让 B 最后返回；从路由变化开始持续显示目标遮罩，最终只能展示 C。加载期间输入、附件、发送、旧 awaiting、plan 和 frontend tool 均不可操作。
7. 让历史加载失败；应显示可重试错误层，来源 Chat 保留在后方且不能提交消息。点击重试成功后恢复目标位置。对当前 Chat 执行 reload 失败时也不得清空现有内容。
8. 在切换请求发出后立即新建空白对话；旧响应不得覆盖空白页。新 Chat 首条 query 获得 canonical `chatId` 时不显示历史切换骨架、不发生第二次加载，并且恢复完成前不聚焦 Composer。
9. 切换前记录折叠状态，随后改变消息文本高度、附件数、折叠状态、容器宽度、主题或根字号；返回时旧 snapshot 与 bookmark 均不得复用，应直接恢复到对话最后。未改变数据和布局时允许 snapshot 加速。
10. 连续访问超过 150 个不同 Surface/Chat 组合后返回最早项，确认最旧书签已淘汰且应用稳定；删除 Chat 或切换 Gateway 身份后，对应书签不得恢复。

## 公开对话分享回归

1. 通过公开边缘网关直接打开 Tunnel 返回的 `/share/share_xxx`，Network 中应只有主文档和 `/assets/conversation-export/<hash>/` 下的显示资源，不加载 WebClient 主应用 bundle、不建立 `/ws`，也不初始化 Token Bridge。
2. 正常响应必须是 `text/html; charset=utf-8`，正文与 Platform 上传字节一致，并包含 `no-store`、`nosniff`、`noindex` 和 `no-referrer` 响应头。
3. 使用包含中文、GFM、KaTeX、代码、ECharts、Mermaid 和原始 HTML 的完整文档验证正文、复制、折叠思考和图表降级；危险内容仍由导出模板的集中净化边界约束。
4. 撤销、到期、随机合法 ID 和非法 ID 均返回同一最小 404 HTML，不加载远程资源；页面不显示“打开 App”或下载客户端 CTA。
5. 执行生产构建并检查产物清单，确认没有 `share/` HTML、JS 或 CSS 入口，且 WebClient 代理配置不处理 `/share/*`。

## 静态 HTML 导出回归

1. 分别从 Chat Actions 和 History Modal 执行“导出静态 HTML”，确认浏览器并行请求 Platform `format=snapshot` 与同源 `/export/conversation.template.html`，Snapshot 以 Blob parts 直接进入下载且不调用 `JSON.parse`/`JSON.stringify`；原 Markdown 导出入口保持独立。Desktop HTML 路径由常驻 Worker从 Platform 获取 Snapshot、从 WebClient Host 获取模板。

### 活动 Run 阻断式压缩

1. 在普通 Agent 模型流输出期间分别触发 L1/L2，确认页面先显示“等待当前步骤完成”；当前 Turn 自然结束且收到 `context.compact.start` 后，L1 切换为“正在压缩工具上下文”，L2 切换为“正在生成上下文摘要”。
2. 在工具执行期间通过顶部菜单触发，确认已启动工具批次全部完成并且只执行一次，结果持久化后才在下一次模型调用前压缩。
3. 在 approval/question/form 等待期间压缩，确认 awaiting 标识不变，压缩后返回原等待状态，提交答案后继续原 Run。
4. 压缩成功时确认 `scope:"run"` 和 level 正确，时间线按 `compactId` 各只有一条完成消息，Context Window 更新为 `postCompactEstimatedTokens`。连续 L1/L2 后使用最新 checkpoint。
5. 压缩请求等待期间 Interrupt 仍可用；Interrupt 后压缩请求显示 `run_interrupted`，不伪造成功事件。
6. 刷新或重新进入 Chat，确认 `_type: "compact.run.checkpoint"` 只回放一条公共完成事件，不泄露私有消息快照，后续 Query 使用 checkpoint 上下文。

### 跳过、冲突与禁用态

1. 对无完整白名单工具组的 Chat 执行 L1，确认 `skipped/no_compactable_tools`；对不存在尚未压缩终态历史的 Chat 执行 L2，确认 `skipped/no_compactable_history`。两者都只显示普通提示，不产生 `context.compact.complete`，不修改 Context Window。单个已结束的大 Run 可用 L2 压缩；只有最近 5 次工具调用时 L1 正常跳过，不能解除硬保护。
2. 使用 mock 注入 `detail: "history_changed"`，确认页面提示“对话历史已变化，请重试压缩”，不伪造成功事件、时间线或用量更新。
3. 注入 WebSocket 断开、Platform 4xx/5xx 或空响应，确认显示失败提示，Platform 模式不在业务/传输失败后偷偷回退 HTTP。
4. 在普通 Agent 或 Team 协调器的原生根 Run 期间，确认顶部菜单与三个命令入口仍可用；快速连续点击时只允许一个进行中的 compact 请求。ACP、Proxy、Channel 或 BTW 活动 Run 应显示 `unsupported_active_run`，不尝试重写活动历史。
5. 当已有 compact 请求时，相同 `requestId` 重试应返回同一结果，不同请求返回 `accepted: false/status: "busy"/detail: "compact_in_progress"`；页面不产生重复完成时间线。
6. 注入 L2 模型失败或空响应，确认分别显示可重试的摘要生成失败且无成功事件；注入 `summary_input_too_large`，确认提示投影后的历史仍超出单次摘要预算，不再反复建议执行 L1，不显示旧的规则兜底来源。
7. 使用小 Context Window 触发自动压缩，确认顺序固定为 L1→重新估算→必要时单次 L2；80% 触发 L1、硬保留最近 5 次及边界并行批次；L1 后低于 90% 不得调用 L2，达到 90% 才执行摘要，自动 L2 失败时不得继续下一次普通模型调用。

## 会话整体切换与竞态

1. A 含产物、计划和任务，切换到慢响应且无这些字段的 B：从第一帧起 timeline、artifact、plan-tasks 统一占位；顶部不显示 A 的信息，输入框保留草稿但不能发送、添加附件或提交旧 HITL，侧栏可继续切换。数据完成、最短保持和淡出结束后同时解锁，B 中不残留 A。
2. 分别让 Agent 初始化不返回/失败、历史请求未发起/不返回、历史请求连续失败：目标接收起最多 15 秒进入明确错误态，错误时旧内容仍隐藏。点击重试仍加载同一目标，seq 增长、截止时间更新，旧响应不得覆盖新事务。
3. 使用受控 Promise 复现 A → B → C、B 迟到、超时后迟到、重试成功后旧结果返回。以真实 Provider、Router、Shell 和三个区域组件的联动测试验证身份与展示状态，不只验证工具函数。
4. 有效原始 query promotion 不回放历史；过期 promotion 与 attach 不能单独跳过历史。切入活动 Chat 仍完成统一占位退出；同 Chat 后台刷新不遮蔽 live 内容。隐藏页面后越过截止时间，再激活立即显示超时。
5. 模拟不稳定尺寸，滚动恢复最多 2 秒退出；分别检查正常动画、减少动态效果设置、退出途中再次切换、错误与重试，以及所有发送入口和旧 awaiting 的迟到提交结果。
6. macOS 与 Windows 分别验证隔离构建和安装流程；比较 Program bundle、Desktop 同步资源、打包应用、实际部署 dist 的 HTML/JS/CSS 指纹。跨产物生成 ZIP 不等于 Windows 原生验收。安装版还必须复查 Chat `36a49dee-bab7-4e5b-84c7-07e2e3c5a83a`；环境缺失的步骤明确记录为未完成。

## 边界与非目标
